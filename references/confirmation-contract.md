# 确认交付与同步契约（网页）

首次走查生成核对资料；只向用户集中询问会改变结果的不确定项。无未决项直接继续；已确认部分可继续准备，完整生成和部分预览按 [用户流程](user-workflow.md) 的门槛区分。未确认项不得猜测生成。

## 输出目录（固定结构）

```
<项目>/输出/识图确认/
├── 1F设备清单.csv        ① 给用户看、可编辑
├── 1F识图核对.html       主核对入口
├── 1F编号预览.png        ② 给用户看
├── 1F识图摘要.md         ③ 给用户看：分组、排除、原点、问题清单
├── 1F待确认局部.png      ④ 可选：只在有看不懂的块时出
├── project-config.json   ⑤ 交接给网页生成和后续步骤
├── placements.json       ⑥ 交接给生成步骤
└── _过程/                缓存及版本；versions/ 为恢复依据，不当临时文件删除
```

规则：

- **楼层标签统一用 `1F`、`2F`、`B1`**，不用“一楼”“首层”。多个楼层就每层一套 ①–④、⑥，共用一个 ⑤。
- **顶层只放上表这些文件**。统计、文字、视图分布、初览渲染、`<楼层>_inserts.json`、候选插入、资产列表、子设备展开等中间结果一律放 `_过程/`，名字随意。
- HTML 为主核对入口，PNG 为辅助；按 review-html.md 生成交互核对页，默认仅突出待确认项。
- 网页底图缓存放 `_过程/`，与模型使用相同原点和单位。
- 用户确认后先在 `_过程/versions/<revision>/` 留存输入、答案和数据快照，再同步更新当前文件；不在顶层堆 `_v2`、`_确认版`。当前文件是工作视图，不是唯一历史存储。

## ① `<楼层>设备清单.csv`

UTF-8 BOM，Excel 可直接打开。每个插入一行，按分组、Y、X 排序。列名和顺序固定：

```
编号,分组,说明,建议资产,处理,DXF块,动态原名,图层,句柄,中心X_m,中心Y_m,旋转_deg,镜像X,镜像Y,长X_m,宽Y_m,用户确认,用户备注
```

- `编号`：稳定编号 `分组-序号`，例如 `G05-0012`。后续对话、验收都按它引用，生成后不重编。
- `分组`：设备用 `G01…`，排除项用 `X01…`（排除也要成行，方便用户核对）。
- `处理`：采用新版 `已识别`、`已确认`、`排除`、`待确认`；旧 `生成` 仅表示拟生成，不等于用户确认。
- `镜像X/镜像Y`：1 或 -1。
- `用户确认`、`用户备注` 留空给用户填。

## ② `<楼层>编号预览.png`

用 `scripts/preview_numbered.py` 从 ① 直接生成，不要另写绘图代码：

```
python scripts/preview_numbered.py 1F设备清单.csv --out 1F编号预览.png \
    --title "1F 设备分组预览（单位 m，原点=DXF(x,y)mm）"
```

效果：按分组着色的矩形平面，每组第一个位置标粗体分组号，“待确认”项用红字标编号，右侧图例为“分组 说明”，“排除”项不画。标题写明单位和原点。脚本只读 `编号, 分组, 说明, 处理, 中心X_m, 中心Y_m, 长X_m, 宽Y_m` 这几列。

## ③ `<楼层>识图摘要.md`

固定四节，内容和对话里给用户的一致：

```markdown
# 1F 识图确认

状态：尚未生成待确认部分的三维场景。<一句话：已确认什么、还缺什么>

## 分组
|分组|说明|数量|建议资产|处理|
|---|---|---:|---|---|
|G01|立库托盘货架排|28|横梁货架|已识别|
|X01|图框外托盘线副本|137||排除|

## 坐标
原点：DXF (x, y, 0) mm；主图范围：(x0, x1, y0, y1) mm；单位换算 mm → m。

## 需要注意
<副本偏移、图层混入、组合块展开、数量对不上的地方，每条一句>

## 问题清单
1. G06 堆垛机用哪种？（单立柱 / 双立柱）
2. ……
```

问题只问会改变生成结果的，一次问完、编号，方便用户按号回答。

## ④ `<楼层>待确认局部.png`（可选）

只在有“待确认”的块时出：把这些块在 DXF 里的局部渲染拼成一张，每格标编号和尺寸。用 `dxf_inventory.py render --region` 渲染。

## ⑤ `project-config.json`

基于 `assets/project-config.json`，未知项保持 null。写好 `underlay` 段（底图区域、排除的图层、是否带文字）；墙体图层能认出来的话，把 `walls` 段也写好。

## ⑥ `placements.json`

所有非排除的设备及待定设备项；路径、注记和建筑参考分流保存。以下为最小结构，v1.6 附加字段见文末：

```json
{
  "origin_dxf": [x, y, 0],
  "units": "m",
  "status": "draft | confirmed",
  "placements": [
    {"id": "G01-0001", "group": "G01", "handle": "DDCED", "block": "*U6557", "dyn": null,
     "layer": "0", "cx": 46.75, "cy": 29.314, "rot": 0, "sx": 1, "sy": 1, "w": 91.75, "d": 1.2}
  ]
}
```

坐标已减去原点并换算成 m。`id` 和 ① 的 `编号` 一一对应。

## 本轮结束时的回复

优先给 HTML 主入口和剩余问题，按需给 CSV/配置等辅助链接；无需每轮罗列全部文件。无待办时报告进展并继续已授权步骤，不停下来索要全表确认。不要把 `_过程/` 的缓存堆给用户。

## 问题清单常见条目

- 立库和货架：储位层数、层高、总高（平面图没有时必问）；
- 堆垛机型号（两端图形可能是同一台的极限位；有依据或已有确认时去重，否则集中询问）；
- 没有对应资产的设备怎么处理（代用、简单几何体或不生成）；
- 看不懂的块：给出编号、尺寸和位置；
- 托盘样式；
- 货架是否放货箱或带货托盘：空架 / 局部 / 满货位；需要时确认占用比例、分布、货物外形及尺寸。已有明确要求不重复询问；写入 `rack_contents` 配置，避免把地面带货托盘的确认误当成货架满载授权；
- 只有排除证据冲突或范围不明确时询问；明确的注记、重复图框、范围外楼层记录依据后分流，不重复索取审批。

## 接收校准

- 用户可能直接在对话里回答，不填 CSV，这样也算确认。把答案写回 ① 的 `用户确认` 列和 ⑤，⑥ 逐项更新 `status`；仅全部影响本轮生成的疑点解决后，将总体 `status` 改为 `confirmed`，否则保留 `draft`，③ 的状态行和问题清单同步更新（标上答案）。
- 用户说“不用管”的分组，改为 `排除`，并在 ③ 里记录原因。
- 给了总高、没给必需的储位层数时：保持层数 null 并列为待补录；只有明确批准展示近似时才采用近似层数，并记录依据及范围。
- 改了 ① 后重新生成 HTML 和辅助 PNG；同时刷新摘要、配置、placements 及源清单哈希，不能仅改 UI 状态。

## 网页补充字段与回答合并
保留原 CSV 固定基础列，末尾追加：来源、判断依据、不确定原因、需用户判断、问题分组、确认来源、确认时间、资产ID。使用 UTF-8 BOM；JSON/HTML 使用 UTF-8。旧脚本不认识的字段保留，不丢弃。
每个实体的稳定 ID 在 CSV、placements、HTML 和三维实例之间一致。HTML 导出答复先校验源清单哈希及 ID 集合，再按 ID 合并；文字答复记录原话、适用区域及问题编号。不把一个区域的回答套到其他区域。
固定 `<楼层>` 命名如 1F、2F、B1；多楼层分别保存 `<楼层>placements.json`，单层可用 placements.json。配置共用，所有文件原地同步，不制造确认版副本。历史输入留在 _过程/。
`placements.status` 采用 draft/confirmed；实体另记 recognitionStatus（已识别/已确认/待确认/排除）、evidence、confirmationSource、supportId、ownerId、assetId、assumptions。`recognitionStatus` 表示识别/回答状态，不作为生成开关。仅 `generationStatus=ready` 的设备进入生成；缺失参数保持 null。已确认型号但高度未知仍是 blocked。
摘要固定四节：分组、坐标、需要注意、问题清单。问题只问代理没把握的，按同类问题合并；证据充分的识别及排除无需用户逐个审批，排除理由仍须记录。
货架货物选择写入 rack_contents，至少保存 enabled、occupancy_mode、occupancy_ratio、distribution、cargo_asset、cargo_size_m、pallet_asset、confirmation_source。地面带货托盘的确认不等于货架满载授权。只给总高时储位层数保持未知，只有经允许的展示近似才能叠放，并明确非设计层数。
底图 underlay 保存区域、排除图层、文字显示、统一原点和单位；walls 保存墙/门窗/柱图层、闭合轮廓来源、门洞及高度依据。墙高没有依据时集中询问，不默认 6m。


## JDL 映射附加字段（v1.6）

CSV 固定基础列及原追加列保持兼容，再追加：规范图层、实体角色、映射状态、生成状态、阻断原因、规则集、字典版本、图块属性签名、确认作用域。后两列分别是解析器计算的块定义与属性签名、明确的楼层/区域或项目确认范围；不要用同一常量填满。设备清单中的设备/待定项才进入 placements；路径、注记和建筑参考分别保存，不把非设备标成漏建或混入设备数。

placements 的实体字段补充 `layerRaw`、`layerEffective`、`layerCode`、`role`、`mappingStatus`、`generationStatus`、`blockers`、`mappingId`、`ruleSet`、`sourceDefinitionHash`、`nestedPath`、`physicalId`、`parameters`、`parameterEvidence`、`worldTransform`。保留老字段 `layer` 作为原始图层兼容值。`mappingStatus` 和 `generationStatus` 的值见用户流程；未知参数保持 null，矩阵由解析器计算，不能用审阅矩形中心代替。

总体 `status=draft/confirmed` 是核对工作快照状态，不等于产品 `available`。顶层增加 `workflowState`、`dictionaryVersion`、`ruleSet`、`generationScope`、`partialPreview`、`blockers`。确认答案合并后重新计算门槛，再提交新 revision；生成失败不覆盖上一个 available 版本。
